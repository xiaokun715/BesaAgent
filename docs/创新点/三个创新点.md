这三个创新点可以组织成一套有层次的 AI Agent 系统优化方案，而不是三个相互独立的功能。

- 创新点 1：Agent 组件策略动态组合，解决同一个 Agent 框架如何适配不同任务的问题。
- 创新点 2：Agent 池驱动的动态 Workflow，解决不同任务如何选择 Agent、构建执行图的问题。
- 创新点 3：失败案例驱动的检索与经验协同优化，解决执行失败后如何定位原因、积累经验并持续改进的问题。

三者分别对应组件层、编排层、优化层。第一点决定每个 Agent 内部采用什么策略，第二点决定多个 Agent 如何协作，第三点则利用执行反馈改进前两层。

## 创新点 1：基于组件策略库的 Agent 动态配置与组合

### 1. 核心思想

借鉴 DSH 所体现的可组合、动态选择思想，将 Agent 从固定实现改造成由多个可替换组件组成的系统。

每个组件不再只有一种实现，而是维护多种策略。例如：

| 组件    | 可选策略                          | 适用场景               |
| ----- | ----------------------------- | ------------------ |
| 上下文管理 | 全量保留、滑动窗口、多级摘要、任务状态压缩         | 短对话、长任务、多阶段测试      |
| 记忆机制  | 无状态、会话记忆、向量检索记忆、结构化经验记忆       | 单次问答、连续调试、历史故障复用   |
| 检索策略  | 向量检索、BM25、SQL、混合检索、查询分解       | 技术问答、精确参数查询、复杂故障分析 |
| 工具选择  | 固定工具集、按任务动态选择、基于依赖关系选择        | 单一操作、复杂测试任务        |
| 权限管理  | 只读、受限执行、审批后执行、沙箱执行            | 知识查询、环境操作、自动化测试    |
| 验证机制  | 格式校验、规则验证、工具结果验证、多 Agent 交叉验证 | 用例生成、测试执行、故障诊断     |
| 执行策略  | 单次执行、重试、回溯、候选方案比较             | 简单任务、易失败任务、复杂诊断    |

系统根据任务类型、风险等级、预算和执行环境，从各组件的策略库中选择配置，再组装成适合当前任务的 Agent。

例如：

- 知识库问答：多级上下文压缩 + 混合检索 + 会话记忆 + 引用验证。
- 测试用例生成：需求状态管理 + 协议知识检索 + 约束校验 + 用例格式验证。
- 测试环境操作：任务状态压缩 + 受限工具权限 + 环境状态检查 + 失败恢复。
- 复杂故障诊断：历史案例检索 + 多假设分析 + 日志证据验证 + 必要时回溯。

这里的关键不是简单地配置几个开关，而是将每种策略定义为具有明确接口、输入输出、适用条件、资源成本和质量指标的组件实现。

### 3. 优点与代价

| 维度    | 优点                          | 代价与风险                |
| ----- | --------------------------- | -------------------- |
| 任务适配  | 不同任务采用不同策略，避免所有任务共用一套配置     | 需要建立任务分类与策略选择机制      |
| 性能与成本 | 简单任务采用轻量策略，复杂任务启用更强的验证和推理能力 | 策略选择本身会产生计算与维护成本     |
| 可扩展性  | 新增策略不必重写整个 Agent            | 组件接口、版本和依赖管理更复杂      |
| 可测试性  | 可以独立评估单个策略，也能对比不同组合         | 组合数量可能呈指数级增长         |
| 可靠性   | 高风险任务可以采用更严格的验证和权限策略        | 错误的策略选择可能降低任务质量或扩大风险 |
| 可解释性  | 能记录每次任务为什么选用某套策略            | 需要保留决策依据、配置版本及运行轨迹   |

最重要的代价是组合空间爆炸。 假设有 6 个组件，每个组件有 4 种策略，理论上就有 \\(4^6=4096\\) 种组合。如果每次改动都要完整测试，验证成本会很高。

可以采用三种方法控制复杂度：

1. 约束合法组合：通过组件契约、依赖约束和权限约束，排除不兼容的策略组合。
2. 场景模板 + 局部动态调整：预先定义知识问答、用例生成、测试执行等配置模板，只动态调整少量关键组件。
3. 基于评测的策略选择：在质量、时延、成本和风险约束下选择策略，而不是让 LLM 无约束地自由拼装。

可以把选择目标形式化为：

\\[ \max\_{\pi \in \Pi} \left( Q(\pi)-\lambda_c C(\pi)-\lambda_t T(\pi) \right) \\]

其中，\\(\pi\\) 是一套组件策略组合，\\(Q\\) 是任务质量，\\(C\\) 是调用成本，\\(T\\) 是时延，\\(\Pi\\) 是满足接口、权限和资源约束的合法组合集合。高风险任务还需要增加安全约束，不能只靠加权目标来平衡。

### 4. 如何体现技术深度

如果只是根据任务类型切换几组预设配置，创新程度有限。更深入的版本应具备：

- 策略标准化：统一组件接口、配置 Schema、前置条件、输出契约和错误语义。
- 策略选择与验证：不仅选择策略，还验证组合是否兼容、是否满足任务要求。
- 运行时可观测性：记录组件配置、策略版本、执行指标和最终结果。
- 策略效果评估：通过离线基准测试比较不同组合，而不是仅凭 LLM 判断哪种配置更好。
- 安全降级：策略选择失败、组件不可用或任务风险升高时，回退到经过验证的默认配置。

这样，项目就从“Agent 配置管理”提升为一个具有策略注册、动态装配、约束校验和效果反馈的 Agent 组件运行时框架。

## 创新点 2：基于 Agent 池的动态 Workflow 生成与执行

### 1. 核心思想

将 Agent 从固定 Workflow 中解耦出来，建立统一的 Agent Pool。系统根据任务目标、已有输入、Agent 能力、前置依赖和执行约束，选择部分 Agent，动态构建 DAG（有向无环图）并执行。

它需要支持三种工作模式：

| 模式            | Workflow 来源          | 典型场景                     |
| ------------- | -------------------- | ------------------------ |
| 预定义 Workflow  | 人工设计、版本化管理           | 完整测试分析与执行                |
| 模板化 Workflow  | 预定义骨架 + 参数化裁剪        | 已有测试用例，只执行环境准备、测试执行和结果分析 |
| 自动生成 Workflow | 根据任务目标与 Agent 能力动态规划 | 临时测试评估、专项验证、未知组合任务       |

三种模式不是相互替代的关系。生产系统可以优先采用预定义 Workflow，在确定性较高的场景中执行；对有明确模板但输入不同的任务进行模板裁剪；仅在需求变化大、没有合适模板时才生成新 Workflow。

Agent Pool 不只是 Agent 实例的集合，还需要维护能力元数据，例如：

- 输入输出契约：输入数据类型、必需字段、输出 Schema。
- 前置条件：需要哪些输入资产、环境状态或上游结果。
- 执行属性：是否支持并行、是否有副作用、是否允许重试。

Workflow Planner 根据任务目标选择节点并连接依赖；DAG 校验器检查输入输出是否匹配、依赖是否闭合、是否存在环路，以及权限和资源约束是否满足。通过校验后，调度器才执行节点。

### 3. 关键技术点

第一，Agent 能力匹配与节点选择。

不能仅依靠 LLM 根据 Agent 名称选择节点。更可靠的方式是先通过能力标签、输入输出 Schema 和前置条件进行候选过滤，再结合语义匹配与成本估计排序。

例如，用户给定已有测试用例，系统应识别出“需求分析”和“用例生成”可能不再需要，而“环境检查—测试执行—日志分析—结果验证”仍然需要执行。

第二，Workflow 依赖关系推导。

节点选择只是第一步，更难的是确定执行顺序和数据依赖。例如：

- 测试执行依赖环境准备完成。
- 日志诊断依赖测试执行结果和日志。
- 缺陷归因依赖诊断证据，不能仅依赖模型生成的结论。
- 不同测试用例之间若不存在共享状态或资源冲突，可以并行执行。

因此，Workflow 生成需要区分两类依赖：

- 数据依赖：下游需要上游产出的数据。
- 资源与状态依赖：即使没有数据传递，也可能因为共享测试环境、设备或配置而必须串行。

第三，动态 Workflow 的执行控制。

DAG 生成后仍然可能出现运行时异常，需要调度器维护节点状态，例如 `PENDING`、`READY`、`RUNNING`、`SUCCEEDED`、`FAILED` 和 `SKIPPED`。

执行过程中应支持：

- 满足依赖的节点并行执行。
- 失败节点按照错误类型决定重试、跳过、回退或终止。
- 上游输出发生变化时，只重跑受影响的下游节点。
- 通过检查点记录中间结果，避免整个 Workflow 从头执行。

第四，自动生成的 Workflow 如何复用。

自动生成的 Workflow 不能未经验证就直接进入生产环境。可以将它分为两个阶段：

1. Planner 生成候选 DAG，并输出每个节点的选择理由、输入输出和依赖关系。
2. Validator 检查其正确性与风险，经过试运行或人工审批后，才允许执行或保存为可复用模板。

这让 Workflow 不再只是一次性的推理结果，而是可以逐步沉淀为版本化、可测试的工作流资产。

### 4. 优点与代价

| 维度    | 优点                               | 代价与风险                 |
| ----- | -------------------------------- | --------------------- |
| 灵活性   | 根据任务裁剪或生成执行流程，减少不必要的 Agent 调用    | 自动生成的 DAG 可能不完整或依赖错误  |
| 复用性   | Agent 能力与业务流程解耦，节点可跨 Workflow 复用 | 需要维护统一的能力描述和输入输出契约    |
| 执行效率  | 独立节点可以并行，失败时可以局部重跑               | 并行可能造成设备争用、状态冲突和资源超卖  |
| 可维护性  | 预定义流程与动态流程共用执行引擎                 | 调试和追踪跨节点依赖更复杂         |
| 可扩展性  | 新增 Agent 后可以被不同任务复用              | 新 Agent 的加入可能改变已有调度结果 |
| 自动化程度 | 可以把临时测试需求转化为候选执行图                | 需要验证器、权限控制和失败恢复机制     |

### 5. 与传统 Workflow 的本质区别

传统 Workflow 的主要逻辑是：先定义流程，再把任务放进流程。

动态 Workflow 的逻辑是：先理解任务，再根据可用能力构建或裁剪流程。

不过，动态并不意味着越自由越好。完全由 LLM 临时生成并直接执行，会增加不可预测性和调试难度。更稳妥的工程路线是：

1. 先实现预定义 DAG 和标准执行引擎。
2. 增加基于任务输入的 Workflow 裁剪。
3. 增加基于 Agent 能力注册表的自动生成。
4. 最后引入历史执行数据驱动的 Workflow 选择与优化。

真正有技术含量的部分是能力匹配、依赖推导、DAG 校验、资源调度、局部恢复与结果验证，而不只是让 LLM 输出一张流程图。

## 创新点 3：失败案例驱动的检索与经验协同优化

### 1. 核心思想

将 Agent 的失败从一次性的错误处理，转变为可验证、可归因、可复用的经验积累过程。

传统 RAG 优化通常关注文档召回和答案质量；传统 Agent 重试机制通常关注当前任务能否继续执行。这两种方式都可能忽略一个问题：为什么任务失败、失败由哪个环节引起，以及这次失败能否帮助后续任务做得更好。

因此，可以建立一个闭环：

失败检测 → 错误分类 → 证据收集 → 因果归因 → 定向恢复 → 经验沉淀 → 检索复用 → 效果验证。

这里的“因果归因”需要谨慎定义。系统可以根据执行轨迹、对照实验和依赖关系识别有证据支持的原因，但不能把 Critic Agent 的判断直接当成真实因果结论。

其中有两个重要边界：

- 验证器负责判断结果是否满足客观约束。 例如，测试用例是否符合字段 Schema、环境是否真正就绪、命令是否执行成功、日志中是否存在目标错误。
- Critic Agent 负责提出解释与改进假设。 例如，是否因为需求解析遗漏了一个协议约束，导致测试用例生成错误。

Critic 可以帮助缩小排查范围，但应由规则、工具返回值、测试结果或可复现实验来验证关键结论。

### 3. 第一层：建立可执行的验证器

验证器不应只检查最终答案是否“看起来合理”，而要尽可能检查可观测、可复现的事实。

| 验证对象 | 验证方法              | 示例               |
| ---- | ----------------- | ---------------- |
| 需求解析 | 必需字段、约束覆盖率、来源引用   | 测试要求是否遗漏触发条件     |
| 测试用例 | Schema、规则、需求追踪关系  | 前置条件、步骤、预期结果是否完整 |
| 环境准备 | API 返回值、设备状态、版本信息 | 测试环境是否真实可用       |
| 工具执行 | 返回码、状态查询、产物检查     | 命令是否执行成功，产物是否存在  |
| 测试结果 | 断言、日志规则、预期结果对比    | 是否满足测试通过条件       |
| 故障诊断 | 证据引用、结论一致性、可复现性   | 根因是否得到日志或实验支持    |

验证器应该输出结构化结果，而不是只输出自然语言。例如：

```
{
  "stage": "test_execution",
  "status": "failed",
  "error_type": "environment_not_ready",
  "evidence": ["environment_status=initializing"],
  "retryable": true,
  "recovery_action": "wait_and_recheck"
}
```

这是示意结构，实际项目中需要定义统一的错误码、证据格式和恢复动作契约。

### 4. 第二层：建立分层错误分类体系

错误分类的价值在于决定后续采取什么动作，而不是仅仅给失败贴标签。

可以按以下维度分类：

| 一级类别   | 二级类别示例            | 典型处理方式           |
| ------ | ----------------- | ---------------- |
| 需求理解错误 | 条件遗漏、约束冲突、需求歧义    | 补充检索、重新解析需求      |
| 知识检索错误 | 召回遗漏、版本不匹配、证据冲突   | 查询改写、扩大检索、版本过滤   |
| 用例生成错误 | 格式不合法、覆盖不足、预期结果错误 | 规则修正、局部重新生成      |
| 环境错误   | 资源不可用、版本不匹配、初始化失败 | 等待、重新申请、环境重建     |
| 工具执行错误 | 参数错误、权限不足、超时      | 修正参数、申请授权、受控重试   |
| 测试本身失败 | 被测软件异常、断言不满足      | 分析日志、定位缺陷，不应盲目重试 |
| 诊断错误   | 证据不足、原因误判、结论矛盾    | 补充证据、比较候选假设      |
| 流程编排错误 | 依赖缺失、顺序错误、状态传递失败  | 修正 DAG、恢复受影响节点   |

还需要加入第二个维度：错误的可恢复性。例如，环境初始化超时可能适合有限重试；需求本身存在冲突时，反复调用同一个 Agent 通常无效；权限不足时，系统应请求授权，而不是不断重试。

因此，恢复决策应至少综合错误类型、失败证据、重试次数、剩余预算和操作风险。

### 5. 第三层：轨迹诊断与因果归因

一条完整的 Agent 执行轨迹至少需要记录：

- 任务输入和目标。
- Agent、Skill、工具及其版本。
- 每个节点的输入、输出和状态。
- 检索到的文档、引用和版本。
- 工具调用参数、返回值及错误信息。
- 上下游依赖关系、重试历史和最终验证结果。
- Token 消耗、执行时延和资源使用情况。

当任务失败时，先根据依赖图确定失败节点及其上游，再由 Critic Agent 结合轨迹提出原因假设。

例如，测试用例不符合预期，可能存在三种解释：

1. 需求解析遗漏了某项约束。
2. 检索返回了旧版本协议文档。
3. 用例生成阶段没有遵循已提供的约束。

系统可以分别检查需求解析结果、文档版本与引用、用例生成输入输出。证据不足时，再进行有针对性的对照实验，例如固定需求和模型，仅更换检索文档版本，观察失败是否复现。

需要区分三个层次：

- 相关性线索：某个节点失败与最终结果失败同时出现。
- 原因假设：根据轨迹推断该节点可能导致后续错误。
- 经验证的原因：通过规则检查、对照实验或复现验证，获得更强的因果证据。

这比直接让 Critic 总结“失败原因”更加可靠。

### 6. 第四层：从失败案例提炼可复用经验

并不是每次失败都值得写入经验库。一次性的环境波动、缺乏证据的模型猜测，以及已经过期的版本信息，都可能污染经验库。

建议将经验设计成结构化对象：

```
{
  "scenario": "5G测试环境初始化",
  "symptom": "执行前环境仍处于初始化状态",
  "conditions": {
    "stage": "environment_preparation"
  },
  "evidence": ["environment_status=initializing"],
  "root_cause": "待验证或已验证的原因",
  "recovery_strategy": "等待后重新检查环境状态",
  "validation": {
    "reproducible": true,
    "success_rate": 0.95
  },
  "scope": {
    "environment_version": "适用版本"
  }
}
```

其中数值仅用于说明字段含义，不代表实际实验结果。

经验可以分为三类：

- 故障处理经验：某类错误的诊断步骤与恢复方案。
- 成功执行经验：特定任务条件下经过验证的执行路径。
- 策略优化经验：某类任务更适合哪种检索、上下文管理或 Workflow 配置。

经验进入正式经验库前，应经过去重、证据校验、适用范围检查和质量评估。对于存在版本依赖的经验，还需要设置失效条件。

### 7. 第五层：检索与经验协同优化

经验库不应简单地成为另一份向量数据库，而应与原有知识库承担不同职责。

| 维度    | 技术知识库             | Agent 经验库           |
| ----- | ----------------- | ------------------- |
| 主要内容  | 协议文档、设计方案、接口说明、规范 | 执行轨迹、失败模式、恢复步骤、有效策略 |
| 回答的问题 | 系统应该遵循什么规则        | 在类似执行场景下，什么方法曾经有效   |
| 检索方式  | 语义、关键词、SQL、版本过滤等  | 场景匹配、错误类型、环境版本、成功率等 |
| 质量标准  | 权威性、完整性、时效性       | 可复现性、验证证据、适用范围、有效性  |
| 更新方式  | 文档更新与知识加工         | 执行反馈、经验验证、淘汰过期经验    |

执行新任务时，系统先检索相关协议知识，再根据任务特征、历史失败类型和环境版本检索经验。两者共同提供依据，但不能让历史经验覆盖权威规范。

例如，知识库指出某项测试必须满足特定前置条件，而经验库记录了某类环境经常初始化失败。Agent 可以据此提前检查环境状态，但不能因为历史上某些测试曾经跳过该条件，就忽略协议要求。

### 8. 优点与代价

| 维度    | 优点                | 代价与风险                 |
| ----- | ----------------- | --------------------- |
| 可靠性   | 从盲目重试转向分类处理、定向恢复  | 需要建设覆盖关键阶段的验证器        |
| 诊断效率  | 通过轨迹缩小问题范围，减少重复排查 | 轨迹采集、存储和分析存在成本        |
| 经验复用  | 相似任务可以复用经过验证的解决方案 | 错误经验可能被重复传播           |
| 检索效果  | 将静态知识与执行经验结合      | 经验和权威知识可能冲突，需要优先级规则   |
| 持续优化  | 通过回归评测判断策略修改是否有效  | 必须维护基准任务、对照实验和经验淘汰机制  |
| 自进化能力 | 系统可以持续改进策略、检索和流程  | 如果缺乏质量门控，自动更新可能导致性能退化 |

### 9. 怎样才算真正形成闭环

完整闭环不等于把失败日志写入数据库。至少需要完成以下流程：

1. 识别失败，并产出结构化错误信息。
2. 结合轨迹和证据提出原因假设。
3. 通过验证器或实验验证原因与恢复方案。
4. 将有效经验写入经验库，附带适用条件和版本。
5. 在后续相似任务中检索并应用经验。
6. 通过成功率、恢复率、重试次数、诊断时延等指标，比较使用经验前后的结果。
7. 如果经验无效或产生负面影响，将其降权、停用或回滚。

这才是可验证的经验积累，而不仅是让 LLM 自动生成“经验总结”。
