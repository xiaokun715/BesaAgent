# 03 调研笔记 —— `src/gateway`

## 项目解决的核心问题

BesaAgent 是一个**面向软件测试全流程的多智能体平台**（需求 → 测试设计 → 用例 → 环境 → 执行 → 分析 → 缺陷）。
`src/provider` 层解决了「同一个请求在不同厂商 API 上怎么写」，但它是**单厂商视野**的：一次调用只认一个模型，失败就失败。

上层（多个 agent 并发跑测试任务）真正需要的是另一层能力，需求文档 §2 用五个具体诉求表达：

1. 我要的是「**一个够用的模型**」，不是「gpt-4o-mini 这个具体型号」；
2. 这个厂商挂了，能不能**自动换一个**；
3. 多 agent 同时跑，**别把配额打爆**；
4. 这一轮回归跑下来**花了多少钱**；
5. 某个模型连续失败，**别再往上撞**。

痛点场景（具体化）：一次全量回归要跑几千个用例，由多个 agent 并发驱动模型调用。
若每处业务代码自己 `if` 选模型、自己 try/retry，会出现三个可预期的后果：
换模型要全仓库改；故障时各处重试互相叠加成**重试风暴**；无法回答「这轮花了多少钱」。
`需求说明书-gateway.md:39-51` 明确把「唯一入口」论证为这四件事必须收敛的前提。

一句话分工（`需求说明书-gateway.md:37`）：

> provider 管**怎么写**，gateway 管**用哪个、挂了怎么办、花了多少**。

## 竞品/同类项目对比

**未找到定位相当的可比项目。** 这是私有项目的内部模块（`pyproject.toml` license = Proprietary），
没有外部生态痕迹、没有官网、没有社区讨论，WebSearch 无有效素材。

勉强可比的通用方案是 LiteLLM / OpenRouter（多厂商统一调用 + 路由 + 限流 + 计费），
但差异是结构性的而非程度上的：它们是**独立服务 / 独立库**，面向「对外提供统一 API」；
本项目 gateway 是**进程内库**（`需求说明书-gateway.md` D-3 明确选 (a)：进程内调用零网络开销，
对外暴露交给 `apps/server`）。因此报告按用户要求**跳过竞品定位章节**，改用「与通用做法的差异」
的方式在相关章节内联对比（如 §3 的责任链编排 vs 中间件链、§4 的预算对象 vs 各自计数）。

## 为什么需要单独做这个项目

不能用现有方案组合解决，理由是 `NFR-G-04`（故障不放大）这条约束的**强制力层级**不同：

通用做法靠「配置写对」——重试次数配小一点、候选别配太长。
本项目的做法是靠**结构消除一整类 bug**：`CallBudget.try_acquire()` 是**唯一**的计数 API，
retry 与 fallback 都禁止自己数次数（`架构概要设计-gateway.md:155-159`）。
于是「重试 3 × 候选 3 = 9 次上游调用」这个乘积在结构上不可能发生，而不是靠人记得配对。

这个要求来自测试平台的业务特征：**一次回归会并发发起大量调用**，故障放大倍率不是
「多花几毛钱」，而是「一次厂商故障把整轮回归拖垮」。

## 项目背后的组织动机

`docs/` 与源码注释大量引用 `besa-iv-kb`（另一个仓库）的踩坑经验，说明这是同一团队的第二个项目，
gateway 是从上一个项目的经验里**提炼**出来的（见 `架构概要设计-gateway.md:461` R-2 引用 besa-iv-kb
《重构文件结构设计》§2.5、`foundation/__init__.py` 提到该仓库 foundation 曾散在 `core/` 下导致
import-linter 契约被迫开豁免）。所以本模块的许多决策是「上一轮的教训」而非「这一轮的偏好」。

### §9.5 实现阶段回填的修订（R-1…R-8）—— 最有价值的一手材料

这 8 条记录了**编码时推翻设计稿的决定**，是「设计承诺 vs 实现现实」差距的直接证据：

| # | 修订 | 揭示了什么 |
|---|---|---|
| R-1 | 新增 `errors.py`（设计稿只提到缺 `types.py`） | 错误语义既不是数据类型也不该留在编排文件 → 三层「契约+错误+类型」三件套 |
| R-2 | 新增 `src/composition/`，装配收进 `bootstrap.py` | 三个 app 各写一份装配会在「只改其中一份」时开始漂移，症状是「CLI 能降级、服务里不能」 |
| R-3 | `fallback.decide` 判定顺序：「没有下一个候选」排在「预算耗尽」之前 | **顺序写反不报错，只让排障方向跑偏**：默认配置下两者恰好同时发生时，「全部候选失败」被误报成「预算耗尽」，修法完全相反 |
| R-4 | 重试循环同时判**单候选上限**与全局预算 | 只判后者会让一个候选吃掉全部预算，降级链后面的候选永远轮不到 |
| R-5 | 新增 `CircuitBreaker.release()`，`finally` 兜底 | 取消路径上最容易漏；泄漏一个探测位 → HALF_OPEN 探测位被永久占用 → 模型**再也恢复不到 CLOSED**，且日志上只看到「进入半开探测」 |
| R-6 | `degraded` 只表示**运行时故障**导致，缺密钥不计入 | 混同后「没配密钥的环境每次 degraded 都是 True」，这个标记再也无法回答「这次是不是出了故障」 |
| R-7 | `Registry.from_config(provider_options=...)` 测试注入点 | 没有它「401 该不该重试」这类断言在真实网络下无法稳定复现 |
| R-8 | 限流等待边界用 `>=` 而非 `>` | 恰好等到 deadline 才拿到额度同样没用（那一刻预算已归零） |
