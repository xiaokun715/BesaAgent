## 1. 这份文档回答什么

本文只回答三个问题：

1. **provider 层要解决什么问题**，它的边界在哪、什么明确不做；
2. **它对外必须提供哪些能力**（功能需求，编号 `FR-P-xx`）；
3. **什么样的实现算合格**（非功能需求 `NFR-P-xx` + 验收标准）。

**本文不回答**：类怎么设计、方法签名长什么样、文件里放哪些函数。那是《架构概要设计》和《详细设计与任务清单》的事。文中出现的文件名仅用于**圈定职责边界**，不代表最终 API。

## 2. 背景与定位

BesaAgent 是面向**软件测试全流程**的多智能体平台（需求 → 测试设计 → 用例 → 环境 → 执行 → 分析 → 缺陷，即 `src/agent/` 下的七个阶段）。它的每一层都在调大模型：

| 消费方 | 调什么 | 特点 |
|---|---|---|
| `src/agent/` | chat（推理、工具调用） | 高频、要求结构化输出 |
| `src/multiagent/` | chat（多 agent 并发 / 辩论 / 投票） | **并发峰值高**，对限流和成本最敏感 |
| `src/chat/` | chat（流式） | 首字延迟敏感，必须 SSE |
| `src/context/` `src/memory/` | embedding | 批量、维度必须固定 |
| `src/skill/` `src/tool/` | chat 的 tool calling | 依赖厂商工具调用协议 |

如果允许各业务模块直接 `httpx.post(...)` 打各家 API，必然出现三类问题：

1. **同一语义多种写法**——`max_tokens` / `max_new_tokens`、`tools` / `functions`、SSE 增量字段各不相同，业务代码里会长出 `if provider == "dashscope"` 的分支；
2. **重试/超时/错误处理各写一遍**，且逐渐跑偏（哪些状态码该重试、退避怎么算、错误怎么整形）；
3. **换厂商要改业务代码**——这是 `besa-iv-kb`《重构文件结构设计》§2.2 里那条判据（「换一个实现要不要改业务代码」）在模型侧的翻版。

**provider 的定位：把厂商差异收敛在边界内，让上层只看见一套契约。**

一句话说清它和 gateway 的分工：

> provider 只回答「**这个请求在这个厂商的 API 上怎么写、响应怎么读回来**」。
> 至于「**这一次该用哪个模型、失败了怎么办、花了多少钱**」——全部是 gateway 的事。

## 3. 范围

### 3.1 本模块负责

- 定义厂商无关的**统一调用契约**（对话补全、向量化、能力声明、用量、错误分类）；
- 实现 **OpenAI / DashScope / vLLM** 三家适配；
- 厂商 API 的**请求构造与响应解析**（含 SSE 流式解析）；
- 厂商**凭据解析**（`api_key` 直填 / `api_key_env` 环境变量 / 厂商段默认值）；
- **能力声明**（是否支持流式、工具调用、结构化输出、多模态、embedding）；
- 提供 **Mock 实现**，使无密钥 / 无网络环境（单测、CI）能跑通全链路。

### 3.2 本模块明确不负责

| 不做的事 | 归属模块 | 理由 |
|---|---|---|
| 模型选择、路由、优先级 | `src/gateway/router.py` | provider 不认识「业务想要哪个模型」 |
| 失败降级 / 熔断 | `src/gateway/fallback.py` `health.py` | 跨厂商决策，provider 只有单厂商视野 |
| 限流 / 配额 | `src/gateway/rate_limit.py` | 同上 |
| 成本核算 / 记账 | `src/gateway/cost.py` `usage.py` | provider 只透传 usage 原始值，不定价 |
| Prompt 模板、上下文裁剪 | `src/context/` | 与厂商无关 |
| 会话历史存储 | `src/chat/` `src/repo/` | 与厂商无关 |
| 工具定义与执行 | `src/tool/` `src/skill/` | provider 只负责**传输**工具调用协议 |
| 向量存储与检索 | `src/repo/` + 外部知识库 | provider 只产出向量，不存不管检索 |
| 事件发布 | `src/event/` | provider **不发事件**（发了就是跨层耦合）；由 gateway 在边界上发 |

> **一句话记忆**：provider 里**不应该出现** `retry` 之外的策略词、`cost` 字样、以及任何「选哪个」的逻辑。

## 4. 职责边界（按文件圈定）

本模块共 14 个文件，分成**契约层 / 厂商层**两块。厂商层内部再切三刀，这三刀是刻意的：

```
src/provider/
├── base.py          契约层：Provider / ChatModel / EmbeddingModel 抽象
├── types.py         契约层：统一数据模型与能力枚举
├── errors.py        契约层：错误分类体系
│
├── openai/
│   ├── provider.py      厂商描述：base_url、默认模型名、能力矩阵、凭据约定、装配 llm/embedding
│   ├── client.py        HTTP 传输：连接池、超时、代理、SSE 行解析、transport 注入点
│   ├── llm.py           Chat 能力：payload 构造 + 响应解析
│   └── embedding.py     Embedding 能力
├── dashscope/
│   ├── provider.py  client.py  llm.py  embedding.py
└── vllm/
    ├── provider.py  client.py  llm.py
    └── （无 embedding.py）
```

| 文件 | 只该包含 | 明确不该包含 |
|---|---|---|
| `base.py` | 抽象契约、模板方法骨架 | 任何厂商名、任何 URL |
| `types.py` | `Message` `ChatRequest` `ChatResponse` `Usage` `EmbeddingResult` `Capability` 等 | 任何 HTTP / 厂商字段 |
| `errors.py` | 错误基类与子类、`retryable` 判定 | 厂商状态码 → 仅在适配层做映射 |
| `<厂商>/provider.py` | 该厂商的**静态事实**：端点、默认模型、能力、凭据变量名、装配入口 | HTTP 细节、请求构造 |
| `<厂商>/client.py` | **怎么发出去**：连接、超时、SSE 拆行、注入 mock transport | 请求体长什么样、响应字段怎么读 |
| `<厂商>/llm.py` | **发什么、怎么读**：payload 构造、响应 → `ChatResponse`、tool_calls 解析 | 连接管理、重试策略 |
| `<厂商>/embedding.py` | 同上，针对向量化 | — |

**三刀分离的价值**（这是本模块最重要的结构决策，需求层先立住）：

- 换传输实现（`httpx` → `aiohttp`）= 只改 `client.py`；
- 换端点形状（OpenAI 兼容 → DashScope 原生）= 只改 `llm.py` 的构造/解析；
- 新增厂商 = 新建一个目录 + 在 registry 注册，**上层一行不改**；
- `provider.py` 里可以放「能力矩阵」这类纯声明，**它不 import `httpx`**——因此可以在无网络环境下被单测直接断言。

> **`vllm/` 没有 `embedding.py` 不是遗漏，是结论**：vLLM 部署的通常是 chat 模型，向量化走不到它。
> 这直接推导出 `FR-P-08`：**embedding 是可选的、必须能被能力协商拒绝的能力**，
> 而不是「所有 provider 都必须实现 `embed()`，不支持就抛 `NotImplementedError`」。

## 5. 功能需求

需求编号规则：`FR-P-<序号>`。每条给出**要求**与**可验证的验收点**。

### 5.1 统一契约

#### FR-P-01 — 统一的对话补全契约

**要求**：所有厂商的对话能力，都必须能被同一段业务代码调用；业务代码中**不允许**出现厂商名分支。

- 输入至少包含：消息序列、模型名、温度、最大 token 数、是否流式、结构化输出要求、停止词、工具定义、超时。
- 输出至少包含：文本内容、用量（输入/输出 token）、实际模型名、结束原因、原始响应（供排障）。
- 消息角色至少覆盖 `system` / `user` / `assistant` / `tool`。

**验收点**：
- 同一段调用代码，把配置里的厂商从 `openai` 换成 `vllm`，**代码零改动**且能跑通；
- 传入空消息列表 / 非法角色 / 空内容，在**本地**即被拦截并报清晰错误（而非等厂商返回 400）。

#### FR-P-02 — 流式输出

**要求**：支持 SSE 流式返回**增量文本**，并以异步迭代器形式暴露。

- 增量只取**正文**增量；解析上必须容忍非数据行、心跳行、`[DONE]` 结束标记、被拆包/粘包的 SSE 行。
- 流式过程中上游返回错误状态码时，必须**抛出**异常而不是静默返回空流。

**验收点**：给定一段包含空 delta、`[DONE]`、非法 JSON 行的 SSE 报文，产出的增量文本序列与预期完全一致，且不抛异常。

#### FR-P-03 — 工具调用（tool calling）

**要求**：传输厂商的工具调用协议，因为 `src/agent/` 与 `src/skill/` 依赖它。

- 请求侧：能携带工具定义（名称、描述、参数 JSON Schema）；
- 响应侧：能同时表达「模型要求调用工具」（工具名 + 参数）与「模型的自然语言回复」；一次响应可能包含**多个**工具调用；
- 多轮：历史消息中必须能回填工具执行结果（`role=tool` + 工具调用 ID）。

**验收点**：一轮「用户提问 → 模型请求调用工具 → 回填工具结果 → 模型给出最终答复」的完整往返可跑通。

#### FR-P-04 — 结构化输出

**要求**：能要求模型返回 JSON，并保证下游解析不因「模型加了 ```json 围栏」而崩。

- 厂商原生支持 `response_format` 时走原生；**不支持时按声明的能力降级**并在响应中标记「本次未走原生约束」。
- **不猜测 schema**：调用方要求 `json_schema` 但未提供 schema 时，**直接报错**，不做静默降级。

**验收点**：要求 `json_schema` 但不传 schema → 抛明确错误；要求 `json` → 返回可被 `json.loads` 直接解析的内容。

#### FR-P-05 — 推理模型的思考过程处理

**要求**：对返回 `reasoning_content` 的推理模型（如 DeepSeek 系列、Qwen 思考模式）：

- **只取正文**，思考过程不得进入返回内容（否则污染下游结构化解析）；
- 当**正文为空且结束原因为「长度截断」**时，必须**留下明确日志**——这是「思考吃光 `max_tokens`」的典型症状，静默的空答案极难排查；
- 思考过程可选择性地透出到响应的独立字段（供 UI 展示），但**不得**混入正文。

**验收点**：构造一个 `content=""` `finish_reason="length"` 的响应 → 产生告警日志；构造带 `reasoning_content` 的响应 → 返回正文不含思考内容。

#### FR-P-06 — 多模态输入

**要求**：消息内容需支持「文本 + 图片」混合（测试用例截图、缺陷截图是刚需场景）。

- 图片以 URL 或 base64 两种形式表达，由厂商适配层翻译成各自格式；
- 厂商不支持多模态时，**在本地拦截**并报明确错误，不得把图片字段直接透传给上游导致 400。

**验收点**：向不支持多模态的模型发送图片 → 本地报错；向支持多模态的模型发送 → 正常返回。

#### FR-P-07 — 向量化

**要求**：提供 embedding 契约。

- 支持**批量**输入，且批量大小可配（不同厂商上限不同）；
- 声明**向量维度**；维度与配置不一致时必须报错（`besa-iv-kb` 的血泪：`dimension` 必须与向量库 `vector(N)` 对齐，否则写入即失败）；
- 批量请求中**部分失败**的语义必须明确：整批失败并报出失败下标，**不得**返回长度不符的结果。

**验收点**：批量 10 条、其中第 7 条触发上游错误 → 抛出异常并标明是第 7 条，而不是返回 9 条结果。

#### FR-P-08 — 能力声明与协商

**要求**：每个 provider / 模型实例必须能**自述能力**，供 gateway 路由与本地拦截使用：

| 能力 | 含义 |
|---|---|
| `chat` | 支持对话补全 |
| `stream` | 支持流式 |
| `tools` | 支持工具调用 |
| `json` | 支持结构化输出（含是否需要显式 `response_format`） |
| `vision` | 支持图片输入 |
| `embedding` | 支持向量化 |

- 能力来源：**厂商适配层声明 + 配置覆盖**（同一厂商不同模型能力不同，必须允许在模型级改写）；
- 调用方请求了未声明能力 → **本地拦截并报错**，错误信息需指出「哪个模型缺哪个能力」。

**验收点**：对只声明 `chat` 的模型请求 embedding → 本地报错，不发生网络调用。

#### FR-P-09 — 错误归一化

**要求**：把厂商各异的失败统一成一棵可判定的错误树，**至少**区分：

| 类别 | 语义 | 是否可重试 |
|---|---|---|
| 鉴权失败 | 密钥无效 / 无权限 | 否 |
| 请求非法 | 参数错误、上下文超长 | 否 |
| 模型不存在 | 模型名错 / 未开通 | 否 |
| 内容被拦截 | 安全策略拒绝 | 否 |
| 限流 | 429 / 配额耗尽 | 是（但需遵守退避与限流） |
| 上游故障 | 5xx / 502 / 503 | 是 |
| 网络故障 | 连接失败、读超时 | 是 |
| 超时 | 请求整体超时 | 是（但受总预算约束） |
| 被取消 | 调用方主动取消 | **否（必须原样向上传播）** |
| 协议异常 | 响应非 JSON、字段缺失 | 视情况，默认否 |

**验收点**：
- 401 → 分类为「鉴权失败」且**不重试**；
- 503 → 分类为「上游故障」且**可重试**；
- 无法归类的错误 → 落到「未知」类别，**保留厂商原始报文**（截断）供排障，绝不吞掉原始信息。

#### FR-P-10 — 用量透传

**要求**：把厂商返回的 token 用量原样透传给上层（含缓存命中 token，若厂商提供）。

- **provider 不做任何计价**；
- 厂商不返回用量时，**不得编造**——如实标记为「未知」（gateway 会据此决定是否估算）。

**验收点**：上游响应不含 `usage` 字段 → 返回的用量为「未知」而非 0，且不抛异常。

### 5.2 传输与可靠性

#### FR-P-11 — 传输级重试

**要求**：**仅**处理「网络抖动」这一层重试：

- 只重试 `FR-P-09` 中标记为可重试的类别；不可重试的 4xx **立即失败**（重试只是白烧配额）；
- 指数退避；
- 重试次数、退避基数、单次超时可配。

> ⚠️ **与 gateway 的重试必须不叠加**。这是本模块最容易埋的坑：
> provider 每请求重试 3 次 × gateway 每跳重试 3 次 × 降级链 3 个模型 = 最多 27 次上游调用，
> 一次故障会被放大成一场重试风暴。**必须**有一条明确的约定（见 §9 决策点 D-1）。

**验收点**：连续两次 500 后成功 → 总耗时符合退避曲线且最终成功；收到 400 → 立即失败，仅一次调用。

#### FR-P-12 — 凭据解析

**要求**：按固定优先级解析密钥，且**本地部署无密钥是合法状态**：

```
模型级 api_key  >  模型级 api_key_env  >  厂商段 api_key_env  >  厂商约定环境变量
```

- 云厂商（openai / dashscope）必须有密钥，缺失时**构造即失败**（fail fast，不要等到第一次调用）；
- 本地端点（vLLM / 自建）**允许无密钥**，且**不得**发送空的 `Authorization` 头（应完全不发该头）。

**验收点**：配 vLLM 地址但不配密钥 → 正常构造、正常调用、请求头中无 `Authorization`；配 OpenAI 但不配密钥 → 构造期即报错。

#### FR-P-13 — 客户端生命周期与连接复用

**要求**：

- HTTP 客户端**复用**（连接池），不得每次调用新建连接；
- 支持从外部注入客户端实例——这是单测使用 mock transport 的唯一入口；
- 提供显式的关闭/释放语义，且可被 `async with` 管理。

**验收点**：单测中注入 mock transport，全程零真实网络请求。

#### FR-P-14 — 超时、取消与并发

**要求**：

- 单次调用的超时**可配**；
- 调用方取消（`asyncio.CancelledError`）必须**原样传播**，**绝不**被 `except Exception` 吞掉或转成普通错误；
- 同一实例可被多个协程并发使用（无共享可变状态）。

**验收点**：调用中途取消 → 抛出 `CancelledError`（而非被包装成通用错误）；并发 50 个请求无串扰。

#### FR-P-15 — Mock 实现

**要求**：提供无网络、无密钥、确定性的假实现。

- 可返回**固定内容**或**可编排的响应序列**（方便测试「第一次失败、第二次成功」这类路径）；
- 可模拟各类错误、模拟流式分片、模拟空正文 + 长度截断等异常响应；
- 与真实实现**同一契约**，上层无感知。

**验收点**：设置环境为测试态时，全链路可在无网络环境跑通（这是 CI 能跑的前提）。

## 6. 非功能需求

> 编号 `NFR-P-xx`。这些是**结构约束**，比功能需求更容易被违反，因此单列。

| 编号 | 需求 | 说明 |
|---|---|---|
| `NFR-P-01` | **全异步** | 契约必须全部是 `async`。同步实现会阻塞事件循环，而多 agent 场景天然高并发。 |
| `NFR-P-02` | **依赖单向** | provider **不得** import `gateway` / `agent` / `memory` / `repo` / `event` 等任何同仓库模块。反向依赖一旦出现，就是循环依赖的开始。 |
| `NFR-P-03` | **可测试** | 真实实现必须能在**不联网**的前提下被单测完整覆盖（靠注入 mock transport）。 |
| `NFR-P-04` | **密钥不泄漏** | API Key **不得**出现在日志、异常消息、`repr()` 中。错误信息可以含 URL 与模型名，**不得**含密钥。 |
| `NFR-P-05` | **无密钥可启动** | 缺失密钥的情况下，整个应用**必须能正常启动**（只是对应模型不可用），不得在 import 期崩溃。 |
| `NFR-P-06` | **契约先于实现** | `types.py` / `errors.py` / `base.py` 不得 import 任何厂商子包。 |
| `NFR-P-07` | **可配置覆盖** | 端点、模型名、超时、重试、代理等，任何环境相关的值都必须来自配置而非硬编码。 |
| `NFR-P-08` | **类型标注** | 公开接口必须有完整类型标注，且通过静态类型检查。 |

## 7. 配置需求

沿用 `besa-iv-kb` 已验证的两段式：**厂商段（共享 base_url 与凭据）+ 模型段（引用厂商并覆盖）**。

```yaml
providers:
  openai:
    base_url: https://api.openai.com/v1
    api_key_env: OPENAI_API_KEY
  dashscope:
    base_url: https://dashscope.aliyuncs.com/compatible-mode/v1
    api_key_env: DASHSCOPE_API_KEY
  vllm-local:
    base_url: http://127.0.0.1:8000/v1
    # 本地端点：不配密钥

models:
  chat-default:
    provider: openai
    model: gpt-4o-mini
    type: openai
    temperature: 0.0
    max_tokens: 8192
    timeout_s: 120
    retries: 2
    capabilities: { stream: true, tools: true, json: true, vision: true }
  emb-default:
    provider: dashscope
    model: text-embedding-v3
    type: dashscope
    dimension: 1024
    max_batch: 32
```

**要求**：

- `R-1` 密钥**只以环境变量名**的形式出现在配置文件中，值放 `.env`（已 gitignore）或进程环境；
- `R-2` 模型级显式值**覆盖**厂商段默认值；
- `R-2b` **`provider` 与 `vendor` 是两个字段**（实现阶段补充，见《架构概要设计-provider》§9.5 R-1）：
  `provider` 选**适配器**（协议形状：`openai` / `dashscope` / `vllm` / `mock`），
  `vendor` 选 **`providers:` 段的条目**（端点与凭据），缺省时取 `provider`。
  需要分开的是「走 OpenAI 兼容协议、但端点和密钥是自己的」那类厂商 ——
  DeepSeek / SiliconFlow / Moonshot 都是：

  ```yaml
  chat-deepseek:
    provider: openai        # 适配器：OpenAI 兼容形状
    vendor: deepseek        # 端点与凭据：取自 providers.deepseek
    model: deepseek-runtime
  ```
- `R-3` `capabilities` 可被配置覆盖（反映同一厂商不同模型的真实差异）；
- `R-4` 配置缺失时给出**可定位的**错误（指出缺哪个字段、哪个模型）；
- `R-5` 环境切换方式沿用 `base.yaml` + `<env>.yaml` 深度合并。

> **A-6 已在实现阶段修订**（原文为「按退避重试，最终成功」）。
> 原因是《架构概要设计-provider》§4.2 确定了重试边界 D-1：
> **provider 只重试网络层错误（连接失败 / 读写超时），HTTP 状态码错误一律上抛**。
> 理由有两条：厂商故障需要**跨模型**决策（换模型往往比锤同一个更有用）；
> 且 provider 的重试会与 gateway 的重试**相乘**，是重试风暴的主要来源。
> 架构文档是更晚、更具体且带理由的决策，以它为准。
>
> 与之对应的**网络层**重试仍然成立：连接失败两次后成功 → 按退避重试并最终成功。

## 9. 决策点（需评审确认）

> 这几条会显著影响后续详细设计，**建议在进入架构设计前定稿**。

| 编号 | 决策点 | 备选 | 建议 |
|---|---|---|---|
| **D-1** | **provider 与 gateway 的重试如何不叠加** | (a) provider 完全不重试，全部交给 gateway；(b) provider 只重试网络层错误（连接失败/读超时），HTTP 状态码错误交 gateway；(c) 二者独立，靠 gateway 限制总尝试数 | **(b)** —— 网络抖动在传输层处理最自然，HTTP 层错误需要跨模型决策，归 gateway。**并强制**：gateway 侧必须设「总尝试次数上限」兜底 |
| **D-2** | DashScope 走兼容模式还是原生协议 | (a) OpenAI 兼容端点；(b) 原生 DashScope SDK/协议 | **(a) 优先**，原生差异（如 `qwen` 专属参数）在 `llm.py` 内单独处理，避免引入厂商 SDK 依赖 |
| **D-3** | 是否引入 `foundation` 层 | 新仓库当前**没有** `foundation`（配置/日志/错误/ID），provider 与 gateway 都要用 | **建议补**，否则 `src/provider/types.py` + `src/gateway/*` + `src/repo/*` 会各造一套配置与错误基类 |
| **D-4** | 是否需要 rerank / vision 独立契约 | `besa-iv-kb` 中 rerank 与 vision 是独立能力组 | 一期**不做**；多模态经 `FR-P-06` 走 chat 的图片输入即可 |
| **D-5** | 计费与"估算 token" | 厂商不返回 usage 时是否本地估算 | 一期**不估算**，如实标记未知（`FR-P-10`） |
| **D-6** | provider 是否发事件 | 是否在调用前后 emit 事件 | **不发**。provider 保持零跨层依赖（`NFR-P-02`），事件由 gateway 在边界统一发 |

## 10. 从 `besa-iv-kb` 继承的经验（必须避免重蹈）

以下都是在 `besa-iv-kb` 中**真实踩过**的坑，本模块在需求阶段就固化为要求：

1. **推理模型的思考计入 `max_tokens`**。设太小会把预算吃光 → 返回 `content` 为空串、`finish_reason=length`，表现为「检索命中却答不出话」。→ 固化为 `FR-P-05`。
2. **只取 `content`，不取 `reasoning_content`**。混入会污染下游结构化解析。→ 固化为 `FR-P-05`。
3. **不可重试的 4xx 立即失败**，重试只白烧配额。→ 固化为 `FR-P-09` / `FR-P-11`。
4. **`response_format` 的 `json_schema` 不猜**，缺 schema 直接报错而不是静默降级成无约束生成（否则下游解析必然失败）。→ 固化为 `FR-P-04`。
5. **本地端点无密钥时不发 `Authorization` 头**，而不是发一个空的 `Bearer`。→ 固化为 `FR-P-12`。
6. **错误整形、重试退避、SSE 解析必须只有一份**，否则每个适配器各写一遍且逐渐跑偏。→ 固化为 `FR-P-02` / `FR-P-09` / `FR-P-11`。
7. **契约与实现分离**，`base.py` / `types.py` 不 import 厂商子包，这样假实现不会被逼着实现用不到的钩子。→ 固化为 `NFR-P-06`。
