# 08 架构洞察与改进建议

## 一、系统性设计哲学（提炼后的表述）

原表述「拒绝静默」是口号层面的。经过五个模块的独立分析后，可以把它说得更精确：

> **把每一个「不知道」都变成一个必须被显式处理的类型，而不是一个恰好能通过编译的默认值。**

三个操作层：

| 层 | 手段 | 例子 |
|---|---|---|
| 类型层 | 用 `None` 表达未知，禁止用 `0` 冒充 | `Usage.output_tokens`、`Cost.amount` |
| 结构层 | 让一类 bug **没有地方可以发生** | `CallBudget.try_acquire()` 是唯一计数 API |
| 词法层 | 让排障方向可分辨 | `exhausted_reason` 区分 `attempts`/`deadline`；`skipped_reason` 区分 `circuit_open`/`rate_limited` |

**结构层那一条是这个项目真正的原创性所在**，也是它值得被学习的地方：
「数次数的地方只有一处，上界才是可知的」——这不是编码规范，是**用 API 形状消灭一整类 bug**。

## 二、全篇最有力的洞察：破口全部集中在跨模块接缝

这是本次分析最重要的结论，也是 07 交叉验证的直接产物。

把「拒绝静默」当作第一原则的项目，找到的**七处破口**是：

| 破口 | 静默的是什么 | 跨了谁的缝 |
|---|---|---|
| 熔断探测位泄漏 | 模型再也回不到 `CLOSED` | `gateway` × `health` × `rate_limit`（三个文件的接缝） |
| 真实上界 8 而非 4 | 故障放大倍率不可读 | `gateway` × `provider` 的**配置** |
| `dropped` 无出口 | 丢了多少数据没人知道 | `gateway` × `repo`（未接通） |
| `alias=""` | 失败记录从逻辑名聚合里消失 | `usage` × `gateway` 的字段填充 |
| `on_stream_started` 只写不读 | 配置开关没有效果 | `fallback` × `gateway` 的调用点 |
| `CIRCUIT_OPENED` 零发射 | 熔断状态变更不可观测 | B-4（只在门面发）与 FR-G-10（要发）的**约束冲突** |
| `reconcile` 零调用 | 限流约束系统性偏松 | `rate_limit` × `gateway` 的调用点 |

**共性是：每个模块内部都守住了自己的纪律，缝的地方没有人的名字。**

这不是「代码质量差」——恰恰相反，这七个模块的**内部**纪律执行得相当好
（零个 `except` 吞取消、26 处显式 `is None`、单测覆盖 B-1…B-16 全部验收点）。
问题出在**职责的归属于结构上不可见**：没有任何一个文件能回答「provider 的重试该不该折进 gateway 的预算」
或「失败记录的 alias 谁负责填」。

**改进建议（成本最低、收益最高的一条）**：给每个跨模块不变量指定一个**归属文件**，
并把它写成该文件的断言或测试。例如「上界可读」这条应该有一个测试：
`assert total_max_attempts * (1 + provider_retries) <= SOME_DOCUMENTED_NUMBER`。

## 三、「如果重新设计」—— 四条具体建议

### 建议 1：把流式当原语，阻塞当收集器（针对 B-3 的真实问题）

M1 的检验结论是「B-3 在精神上成立、字面上要打折」，并指出真正的问题是
**顺序规则有两个实现**（`fallback.py:78-88` 与 `gateway.py:670-671`），而 R-3 专门警告过这处
「写反了不报错，只让排障方向跑偏」。

所以 B-3 应该**正名为「顺序必须只有一份」**，而不是「必须在一个方法里」。
实现路径：把 `stream_chat` 的 `AsyncIterator[StreamEvent]` 当作**唯一原语**，
`chat()` 变成「跑流并收集到末尾」—— 因为流式的表达力**严格强于**阻塞
（阻塞能给的一切流式都能给：把结果放在最后一个事件里）。

**这个方向的附带好处**：流式路径当前完全没有重试（`max_attempts_per_candidate` 在流式上失效，
瞬时抖动被记成降级），统一到流式原语后这条会自然一起修掉。

### 建议 2：把「预约」变成带标识的一等对象（针对限流）

M4 的论证：当前 `reconcile` 用 `tokens[-1]` 的隐含 LIFO 假设，并发下会改到别人的条目且**无报错**。
改成带 `rid` 的预约对象，让 `reconcile(rid)` / `release(rid)` 按标识幂等，
重复归还**返回 `False`** 以暴露错误；`_prune` 到期按预扣值兜底结清，
并在 `snapshot()` 里暴露 `unreconciled` 计数。

**M4 的一个反直觉推论值得单独记住**：
> **只有在回补可靠之后，预估值才敢于偏保守（高估）。**
> 缺 `reconcile` 的真实代价不是「少扣了」，而是「预估器被迫停在偏低一侧」。

### 建议 3：给 `Cost` 加上「为什么未知」

现在 `Cost.amount = None` 无法区分「价格没配」与「用量没返回」——
前者改配置，后者查适配器，**修法完全相反**。这与项目自己记录的 R-3 教训**同构**
（判定顺序错不报错，只让排障方向跑偏）。

加一个 `unknown_reason: Literal["no_price", "no_usage"] | None` 即可，成本极低。

### 建议 4：出口处再兜一次脱敏

M3 核实：脱敏在 provider 构造期 + `GatewayError.__str__` 不含 `raw`，
**已经比 B-16 的要求更强**。建议在 gateway 出口处再兜一次（`redact_secrets`），
理由是「上游新增一个厂商适配器时，B-16 的保证强度会随它变化」——
**把跨模块不变量在自己边界上重新确认一次**，成本一行。

## 四、值得学习的三处设计（正面清单）

| # | 设计 | 位置 | 为什么值得学 |
|---|---|---|---|
| 1 | `CallBudget` 用**同一对象**强制两个上界 | `retry.py:31-114` | 分别计数会产生「次数没超但时间超了」的组合漏洞，双上界分离时这类漏洞无法被结构性排除 |
| 2 | 价格未知在**排序**里当成最差而非最好 | `router.py:126-127` | 同一个 `None` 在不同语境下语义相反：计费里是「未知」，排序里必须**不能占便宜** |
| 3 | 同一件事（估 token）**限流侧做、计费侧不做** | `gateway.py:804-811` | 判断依据极精准：限流侧误差**自我修正**（回补），计费侧误差**永久固化** |

第 3 条尤其值得记住 —— 它把「什么该做估算」这个模糊问题，归约成了一个可判定的条件：
**误差会不会被后续观测纠正。**

## 五、与业界做法的差异（用户已要求跳过竞品章节，此处仅保留必要对照）

| 维度 | 通用做法 | 本项目 | 评价 |
|---|---|---|---|
| 预算/超时 | gRPC 用 `context` 传 deadline，各层自行尊重 | 单一 `CallBudget` 对象强制 | **更强**：绝对时刻 + 唯一计数点，不用靠各层自觉 |
| 限流 | Guava `RateLimiter` 单维 | RPM/TPM/并发三维 + 预扣回补 | 表达力更强，但回补未接线 → **当前低于设计承诺** |
| 熔断 | Resilience4j 按失败率滑动窗口 | 连续失败计数 + 半开「任一失败」 | **更保守也更简单**，在样本量小（2）时比率本来无意义 |
| 计量溢出 | OTel 基数溢出**不丢弃**，折叠成 `overflow=true` 数据点保住总额 | `UsageLedger` 直接丢弃并计 `dropped` | **可反向借鉴 OTel**：账单场景下「总额错比明细错严重得多」 |
| 错误分层 | 多数库直接把厂商异常向上抛 | 三层（foundation / provider / gateway 边界归一化） | **更清晰**：上层只该看见「所有候选都失败」 |
